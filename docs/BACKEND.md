# SwipeIt — серверная часть, первая версия (ТЗ)

> Версия 1.0, 27 ноября 2026. Для Исполнителя. Что и зачем — [PRD.md](PRD.md), архитектура демо — [TECH_SPEC.md](TECH_SPEC.md), вид и поведение — [DESIGN.md](DESIGN.md), режим работы — [briefs/EXECUTOR.md](briefs/EXECUTOR.md).
>
> Это контракт. Где он молчит, сервер ведёт себя как мок-сервер (`frontend/src/shared/api/mock-server/`): его обработчики — эталон поведения. Где документ и мок расходятся, прав документ. Значения «по умолчанию» из §14 действуют, пока владелец или PM не решили иначе.

## 0. Коротко

- Сервер: Node.js + Fastify + PostgreSQL (Drizzle). Код — в `backend/`. Общий с фронтом контракт и чистая логика — в пакете `packages/core`.
- Обработчики сервера пишутся заново. У них та же форма `(ctx, input)`, те же zod-схемы, чистые функции и ответы. Мок остаётся для демо и служит эталоном. Совпадение проверяют общие тесты.
- Вход: анонимный профиль на устройстве с серверным токеном. Потом — вход через Telegram, чтобы открыть профиль на другом телефоне.
- Реальное время — WebSocket, как в LAN. Но событие получает только тот, кого оно касается.
- Ссылки — короткие, с превью для Telegram и WhatsApp. Старые длинные открываются, как раньше.
- Демо на GitHub Pages остаётся в режиме `local` с ботами. Продукт — новый режим `remote` на своём домене.

## 1. Зачем и что входит в первую версию

### 1.1 Что сервер даёт людям

Демо живёт в браузере. Отсюда его ограничения (PROGRESS, «Ограничения демо»):
- бронь гостя с другого телефона владелец не видит;
- план и Санта по ссылке на другом телефоне не открываются;
- очистил браузер — потерял вишлист;
- у всех ссылок одно и то же превью;
- дедлайн плана и жеребьёвка по дате срабатывают, только пока открыта вкладка.

Режим «Локальная сеть» снимает часть ограничений, но только в одной Wi-Fi и без защиты.

С сервером:
- брони видны всем гостям с любых телефонов, владелец сразу видит счётчик;
- вишлист по ссылке живой: человек добавил желание или отметил «Мне это подарили» — гости видят это при следующем открытии;
- планы и Санта работают между телефонами через интернет, в реальном времени;
- дедлайны и жеребьёвка по дате срабатывают по часам сервера, даже когда все телефоны выключены;
- гости видят фото своих желаний владельца;
- профиль переживает очистку браузера и открывается на другом телефоне (после входа через Telegram);
- ссылка в чате показывает «Вишлист Айгерим — на день рождения, 14 марта», а не общее превью.

### 1.2 Что входит в первую версию

- Все сценарии демо между разными телефонами: лента, вишлист, отправка, гость и брони, «Выбери подарок сам», планы, Санта, «Мои даты» и баннер-напоминание.
- Анонимный профиль, вход через Telegram, выход, удаление профиля.
- События по WebSocket.
- Короткие ссылки с превью: текст свой у каждой ссылки, картинка пока общая.
- Каталог из `catalog/`, как сейчас.
- Загрузка фото своих желаний и своих занятий.
- Лимиты запросов, бэкапы, логи, мониторинг ошибок.
- Окружения staging и prod, деплой из GitHub Actions.

### 1.3 Что позже

- Уведомления (Telegram-бот или web push, §14.5). Напоминание о своей дате пока, как в демо, — баннер в вишлисте.
- Партнёрский каталог и обновление цен.
- Приложения iOS и Android (Capacitor), Telegram Mini App.
- Несколько вишлистов, чат, админка, оплата.
- Слияние двух профилей. Перенос данных из демо (§14.6).
- Своя картинка превью для каждой ссылки (мини-открытка с фото).
- Кыргызский язык.

### 1.4 Первая версия готова, когда

Два человека на своих телефонах, в мобильной сети, в разных местах, присылают друг другу ссылки через Telegram. Они проходят 4 сценария DEMO.md без ботов и без ноутбука:
- вишлист → бронь, владелец видит счётчик;
- ссылка-фильтр → ответ;
- план «Прямо сейчас» → барабан;
- Санта на троих → конверт.

Это задача B21.

## 2. Архитектура

### 2.1 Почему не выложить LAN-сервер в интернет

`frontend/lan/server.ts` — хороший прототип: те же маршруты, WebSocket, планировщик, загрузка фото. Но для интернета он не годится:
- **Нет проверки, кто пришёл.** Пользователь — это заголовок `x-user-id`. А `userId` владельца лежит в каждой ссылке на вишлист (поле `o.u` в `share-codec`). Кто получил ссылку, тот может действовать от имени владельца.
- **База — один JSON-файл.** Каждое чтение копирует всю базу (`structuredClone`). Каждая запись проверяет её целиком zod-схемой и переписывает файл. Для 20 человек в Wi-Fi это нормально, для тысяч — нет.
- **События уходят всем.** В событии брони есть `by` — id того, кто бронировал. Тосты с `forUserId` тоже получают все.
- **Ответы открыты по id.** План со свайпами всех участников (`GET /plans/:id`), чужой вишлист (`GET /users/:id/wishlist`) и профиль (`GET /users/:id`) отдаются любому, кто знает id.

### 2.2 Что переиспользуем и как

Обработчики мока работают с базой целиком. `ctx.db.read()` отдаёт всех пользователей, все свайпы и все планы, а `ctx.db.write(mutator)` меняет объект в памяти. Без переписывания под PostgreSQL их не перенести.

| Что | Как переиспользуем |
|---|---|
| zod-схемы и типы (`shared/api/*/types.ts`) | Те же: проверка входа на сервере, типы ответов |
| `ApiError` и коды | Те же плюс три новых (§4.5) |
| Чистые функции: `taste`, `feed` (`rankProducts`), `dates`, `occasion`, правило порога отправки, `computeMatches`, `drawAssignments`, `catalog-parse`, `share-codec`, `format` | Те же, их вызывают обработчики сервера |
| Таблица маршрутов | Становится контрактом в `packages/core`: метод, путь, кто может, в каких режимах. Мок и сервер к нему привязаны, тест ловит расхождение |
| Форма обработчика `(ctx, input) => Promise<output>` | Та же. Меняется `ctx.db`: вместо `DbAccess` — транзакция Drizzle |
| Сами обработчики мока | Не переносятся. Остаются для `local` и `lan`. Сервер повторяет их логику запросами к базе. Совпадение проверяют контрактные тесты (§12) |
| LAN-сервер | Образец для HTTP-слоя, WebSocket (`ws-realtime.ts`), планировщика и загрузки фото (`sniffImage`) |
| Боты | На сервере не нужны (§7) |

Отвергнутый вариант — переписать и мок, и сервер на общий слой репозиториев, чтобы логика была одна. В долгую это правильно, но ломает работающее демо и удваивает первую работу. Вернёмся к нему, если мок и сервер начнут заметно расходиться.

### 2.4 Стек

| Роль | Выбор | Почему |
|---|---|---|
| Среда | Node.js 24 LTS | Node — решение владельца. 24 стоит на машине Исполнителя |
| HTTP | Fastify 5 | Зрелый и быстрый. Готовые плагины для §10: CORS, лимиты, заголовки безопасности. Логи pino и лимит тела встроены. Express тоже подошёл бы, но он медленнее и многое собирается вручную; NestJS для одного сервиса тяжёл |
| БД | PostgreSQL 17 или новее | Совет PM. Транзакции и блокировки строк для гонок (бронь, жеребьёвка), JSONB для вложенного (варианты, фильтры). Управляемый Postgres есть у всех хостингов |
| ORM | Drizzle ORM + drizzle-kit, драйвер `pg` | Схема на TypeScript рядом с zod-типами. Запросы близки к SQL: видно `FOR UPDATE`. Миграции — обычные SQL-файлы в репозитории. Нет отдельного бинарного движка |
| Валидация | zod 4 и свой `parseInput` | Те же схемы, что в моке |

| Токен Telegram | `jose` | Ключи JWKS и проверка подписи JWT |
| Фото | `sharp` | Перекодировать и убрать EXIF (§10) |
| Тесты | Vitest; Postgres в Docker (`docker compose`, в CI — service container) | Vitest уже в проекте, Docker есть на машине Исполнителя |
| Сборка | esbuild → `dist/server.js` | Собирает и TypeScript из `packages/core` |

Новые зависимости сверх списка — только с обоснованием в PROGRESS, как во фронте.

### 2.5 Чем сервер заменяет окружение мока

| В `ctx` мока | `local` / `lan` | Сервер |
|---|---|---|
| `db` | localStorage / JSON-файл, вся база в памяти | Транзакция PostgreSQL, запросы только к нужным строкам |
| `realtime` | BroadcastChannel / WebSocket всем | События копятся в транзакции и уходят **после** commit, только адресатам (§5). Транзакция откатилась — ничего не ушло |
| `clock` | `Date.now()` + перемотка из демо-панели | Настоящее время, без перемотки. В тестах — фиксированные часы. `Date.now()` в обработчиках запрещён правилом eslint |
| `random` | `createCryptoRandom` | Тот же |
| `userId` | sessionStorage / заголовок `x-user-id` | Из сессии по токену (§3.2) |
| `settings` (скорость ботов, задержки, ошибки) | Демо-панель | Нет. Настройки сервера — переменные окружения |
| `catalog` | `fetch` / чтение файлов | Чтение `CATALOG_DIR` при старте тем же `catalog-parse` (§8) |
| `mode` | `local` / `lan` | `remote`: друзья — из таблицы `friendships` (§4.3) |

**Часовой пояс.** TECH_SPEC §6 говорит: дни считаются по календарю Бишкека. Но код (`toDateKey`, `nextOccurrence`) берёт местное время процесса. В браузере это часы телефона. Сервер в облаке живёт в UTC: с 00:00 до 06:00 по Бишкеку он считал бы, что ещё вчера.
- В первой версии процесс сервера запускается с `TZ=Asia/Bishkek` (Dockerfile, скрипты, CI). Это проверяет тест.
- Пользователи из других часовых поясов — позже.

### 2.6 Транзакции и гонки

- Каждый запрос на запись — одна транзакция (READ COMMITTED).
- Сначала блокируется корень того, что меняем: `SELECT … FOR UPDATE` строки `users` (свой вишлист, свайпы, даты), `plans` или `santa_games`. Так два свайпа в одном плане или два «Вступить» в одну игру идут по очереди. `plan:match` не теряется и не приходит дважды.
- Гонку двух броней одного подарка решает уникальный индекс (§4.2): второй получает `CONFLICT` «Кто-то уже выбрал этот подарок».
- Повтор запроса безопасен там, где так уже устроен мок: свайп заменяет прежний; повторная бронь возвращает свою; повторные «Вступить», «Готов», «Открыл конверт» ничего не меняют.

## 3. Аккаунты и вход

### 3.1 Анонимный профиль

Как сейчас (DESIGN §8.1): человек открывает приложение, профиль создаётся сам, под прелоадером, без имени. Имя спрашиваем, когда его увидят другие (`NAME_REQUIRED`).
- `POST /users` создаёт профиль и сессию и возвращает `{ me, token }`. Демо-друзей нет.
- Гостевые экраны (`/w/`, `/pick/`, приглашения) профиль сами не создают, как и сейчас.
- **Гость без профиля бронирует так** (умолчание, §14.8): клиент тихо создаёт профиль (`POST /users`), потом шлёт `POST /reservations` с именем из формы. Сервер кладёт это имя и в бронь, и в профиль. У каждой брони есть автор с токеном, `guestId` из localStorage больше не нужен.

### 3.2 Сессии и токены

- Токен — 32 случайных байта (`crypto.randomBytes`) в base64url. В базе хранится только SHA-256 от него (`sessions.token_hash`).
- Клиент хранит токен в localStorage (`swipeit:remote:token`) и шлёт `Authorization: Bearer <token>`.
- Почему не cookie: фронт и API на разных адресах, а позже будут Capacitor и Telegram Mini App, где cookie неудобны. Цена — риск кражи токена через XSS. Защита — CSP без сторонних скриптов (§10).
- Сессия живёт, пока ей пользуются. Не пользовались 180 дней — закрыта. `last_used_at` обновляется не чаще раза в час.
- Все вкладки одного браузера — один человек. В `remote` нет «Смотреть как» и правила «две вкладки — два участника».
- Неверный или закрытый токен → `401 UNAUTHORIZED`. Клиент **не** создаёт молча новый профиль поверх старого. Он показывает «Сессия закончилась» с кнопками «Войти через Telegram» и «Начать заново» (тексты — PM в DESIGN). Если токена нет вообще — новый профиль, как сейчас.

### 3.3 Вход через Telegram

Зачем: открыть тот же профиль на другом телефоне и не потерять его при очистке браузера.
- Сейчас Telegram предлагает вход по OpenID Connect (`oauth.telegram.org`), старый iframe-виджет в архиве. Проверено по core.telegram.org/bots/telegram-login в ноябре 2026.
- Подготовка: бот у @BotFather. В разделе Login Widget регистрируются разрешённые адреса сайта, там же выдаются Client ID и Client Secret.
- Поток:
  1. на фронте JS-библиотека Telegram Login открывает окно и возвращает `id_token`;
  2. клиент шлёт `POST /auth/telegram { idToken }`;
  3. сервер проверяет подпись по JWKS (`https://oauth.telegram.org/.well-known/jwks.json`), `iss = https://oauth.telegram.org`, `aud` = id бота, `exp`.
- В задаче проверить, принимает ли библиотека `nonce`. Если да — сервер выдаёт его заранее: защита от повтора токена.
- Скоупы: `openid` и `profile` (имя — только подсказкой в поле имени). Телефон не просим. `telegram:bot_access` — только если владелец выберет уведомления через бота (§14.5). Тогда просим сразу, чтобы потом не спрашивать второй раз.
- Привязка:
  - у Telegram-аккаунта ещё нет профиля → привязываем к текущему анонимному, данные остаются;
  - профиль уже есть (вход на втором телефоне) → сессия переключается на него. Анонимный профиль этого телефона остаётся как есть, без слияния. Если в нём есть желания — перед переключением предупреждение (текст — PM).
- Храним только `sub` и время привязки. Имя из Telegram не перезаписывает своё.
- Окно входа не работает при заголовке `Cross-Origin-Opener-Policy: same-origin`. На фронте его не ставить.

### 3.4 Выход, удаление, «Сбросить демо-данные»

- **«Выйти»** (`POST /auth/logout`) закрывает сессию этого устройства. Если Telegram не привязан — предупреждение: «Профиль пропадёт с этого телефона, вернуть его будет нельзя».
- **«Удалить профиль»** (`DELETE /me`) удаляет человека и его данные: желания, свайпы, даты, сессии, привязки, загруженные фото, ссылки, брони.
  - В чужих планах и играх он остаётся строкой «Удалённый профиль» без имени. Его свайпы и голоса удаляются.
  - В Санте после жеребьёвки пара остаётся, но без имени.
- «Сбросить демо-данные», «Войти как демо-пользователь», «Смотреть как» и демо-панель — только в `local` и `lan`. В `remote` их нет.

## 4. Модель данных и API

### 4.1 Общие правила

- id — строки с префиксом, как в моке (`u_`, `wi_`, `rs_`, `pl_`, `sg_`, `pk_`, `d_`, `ca_`) плюс `nanoid(10)`. Типы и zod-схемы фронта не меняются.
- Время — `timestamptz`, в ответах — ISO-строки, как сейчас. «ММ-ДД» — `text` с проверкой формата.
- Цены — целые сомы (`integer`).
- Вложенное, что не ищем и не меняем по частям, — `jsonb`: `variant_choice`, `custom`, `occasion`, `filters`, `taste`, `decision`, `exclusions`, `picks`.
- То, что меняют несколько человек одновременно, — отдельные строки: участники, свайпы и голоса плана, участники и пары Санты, брони.
- Каталог в базе не храним (§8). `product_id` и `activity_id` из каталога — без внешнего ключа.
- Ответы собираются в те же формы, что сейчас. Например, `PlanSession.swipes` собирается из строк `plan_swipes`. Фронт от этого не меняется.

### 4.2 Таблицы

| Таблица | Поля | Ключи и индексы |
|---|---|---|
| `users` | `id`, `name?`, `avatar_color`, `birthday?` («ММ-ДД»), `interests text[]`, `muted_interests text[]`, `audience`, `taste jsonb?`, `seen_hints text[]`, `dismissed_reminders text[]`, `created_at`, `deleted_at?` | pk `id` |

### 4.3 Друзья

В демо друзья — боты, в LAN — все в сети. На сервере ботов нет, нужен свой способ. Экрана «Добавить в друзья» в DESIGN нет.

Умолчание (до решения §14.7) — дружба появляется сама, в обе стороны:
1. вступил в план или Санту по приглашению — друг организатору (не всем участникам: в офисной Санте на 30 человек иначе все увидят дни рождения и вишлисты всех);
2. открыл вишлист по короткой ссылке, будучи с профилем, — друг владельцу. Дружба ставится в момент открытия, а не брони: иначе появление нового друга подсказало бы владельцу, кто бронировал.

Человек должен знать, что стал другом (решение PM к §14.7):
- на гостевом вишлисте `remote` под шапкой — `caption` «Пыльная роза»: «Айгерим появится у тебя в друзьях: вы будете видеть дни рождения и вишлисты друг друга»;
- в приглашении в план или Санту — то же про организатора.

Тексты — DESIGN §8.5 и §8.7–8.8 (PM добавит к B15).

Правила:
- позвать в план или Санту кнопкой (`participantIds`) можно только друзей, остальных — ссылкой (как в моке);
- безымянные профили в списке друзей не показываются (как в моке);
- удалить друга — позже.

### 4.5 Ошибки и версия API

Ошибка — JSON `{ code, message, requestId }` с HTTP-статусом. `message` — по-русски, для экрана, как сейчас.

| Статус | Код |
|---|---|
| 400, 413 | `VALIDATION` |
| 401 | `UNAUTHORIZED` — **новый**: нет токена, он неверный или закрыт |
| 403 | `FORBIDDEN` |
| 404 | `NOT_FOUND` |
| 409 | `CONFLICT`, `NAME_REQUIRED` |
| 429 | `RATE_LIMITED` — **новый** |
| 500 | `INTERNAL` — **новый** в типе (LAN уже так отвечает). Наружу — общий текст, подробности — только в логе по `requestId` |
| 503 | `OFFLINE` — каталог не загрузился, база недоступна |

- Если спрашивающий не должен знать даже о существовании ресурса (чужой профиль, чужой вишлист) — `404`, а не `403`.
- Версия — приставка пути `/v1`. В v1 только добавляем: новые маршруты, необязательные поля. Ломающее изменение — `/v2`, а старую версию держим, пока живут старые PWA.
- `GET /v1/health` отдаёт `minClientBuild`. Сборка фронта старее — экран «Обнови приложение» с перезагрузкой. Клиент шлёт заголовок `x-client-build`, он попадает в логи.

### 4.6 Приватность: правила и обязательные тесты

1. **Владелец вишлиста не узнаёт, кто бронировал.** Ни в одном ответе владельцу (`/wishlist`, `/reservations`, `/share/:code`, `/users/:id/wishlist`) и ни в одном событии нет `reserver_*`. В событиях нет поля `by`. Подсказка «Возможно, тебе подарили это» после даты повода говорит только, какие желания заняты, но не кем.
2. **Пары Санты видит только сам Санта.** `santa_assignments` читает одна функция — «мой подопечный» для пользователя запроса. Ни один ответ и ни одно событие не содержит чужую пару, в том числе для организатора. Логи не пишут тела ответов Санты.
3. **Значимые даты и напоминания — только владельцу.** Другим уходит только `occasion.date` и `preset` (как `occasionForOthers`). День рождения «ММ-ДД» видят друзья и гости вишлиста, как сейчас.
4. **Вкус, «Не моё», подсказки, скрытые напоминания — только себе.**
5. **Чужой профиль и вишлист по id — только друзьям**, иначе 404.
6. **Не участник плана видит только превью**, без свайпов и голосов.

На каждое правило — тест в `backend/test/privacy.test.ts`: через HTTP и WebSocket, двумя-тремя пользователями.

Честно о том, что остаётся:
- участники плана через API видят, кто что свайпнул (как в моке). Интерфейс показывает только счётчики. Решение — §14.9;
- владелец может открыть свою ссылку вторым профилем и увидеть, какие желания заняты (не кем). Так же и в демо;
- человек с доступом к базе видит пары Санты. Шифровать их в первой версии не будем.

## 5. Реальное время

- **Адрес:** `wss://<адрес API>/v1/ws`.
- **Вход.** Первым сообщением клиент шлёт `{ type: "hello", token }`: заголовок в браузерном WebSocket не поставить, а токен в адресе попал бы в логи. Нет `hello` за 5 секунд или токен неверный — сервер закрывает сокет с кодом `4401`. Успех — `{ type: "ready", userId, now }`.
- **Хаб:** `userId → открытые сокеты` (все устройства человека). Подписок клиент не шлёт: сервер сам знает адресатов.
- **События** — те же `RealtimeEvent`, что сейчас: `db:changed`, `plan:match`, `plan:progress`, `toast`. Поэтому подписчик фронта (`RealtimeBridge` в `providers.tsx`) не меняется.
  - Поля `by` наружу нет: фронт его не читает, а в событии брони оно выдаёт бронирующего.
  - `trigger` и `bot:action` наружу не уходят.
- **Событие — только подсказка «перечитай».** В нём области и id, но не данные. Данные клиент берёт через API, где проверяются права.

| Что случилось | Кому событие |
|---|---|
| Профиль изменён (`users`) | сам и друзья |
| Свои желания, свайпы, даты, повод (`wishlist`, `swipes`, `users`) | сам — на других устройствах |
| Бронь или снятие брони (`reservations`, `wishlist`) | владелец вишлиста и автор брони |
| «Мне это подарили» или «Вернуть» (`wishlist`, `reservations`) | владелец и авторы броней на это желание |
| Изменения плана (`plans`, `plan:progress`, `plan:match`) | участники |
| «Организатор отменил решение» (`toast`) | каждый участник, кроме организатора |
| Изменения игры (`santa`) | вступившие и позванные |

- **Гости и экраны приглашений** событий не получают. Там React Query перечитывает данные при возвращении на экран и раз в 30 секунд (`refetchInterval` только на этих экранах). Подписки по ссылке — позже.
- **Сердцебиение:** ping раз в 20 секунд; нет ответа на прошлый — закрыть (как в LAN).
- **Переподключение:** 1 → 2 → 4 → 8 секунд со случайным разбросом ±20%, дальше каждые 8 секунд. При возвращении во вкладку (`visibilitychange`) — сразу. После переподключения — перечитать все запросы, как в LAN.
- **Офлайн** — как в LAN (DESIGN §8.11): тост без автозакрытия, колода и кнопки действий неактивны. Текст — без «ноутбука» (PM). Очереди офлайн-действий в первой версии нет. Статика PWA работает без сети, данные — нет.
- **Один процесс сервера.** Если процессов станет несколько, рассылка пойдёт через PostgreSQL `LISTEN/NOTIFY` или Redis. Интерфейс хаба это позволяет.

## 6. Ссылки

### 6.1 Как сейчас

Вишлист, ссылка-фильтр и ответ несут данные в адресе (`/w/?d=`, `/pick/?d=`, `/pick/answer/?d=`, lz-string). Приглашения в план и Санту — только id. Статический сайт не может собрать своё превью для каждой ссылки (TECH_SPEC §13).

### 6.2 Короткие ссылки

- В `remote` маршруты `POST /wishlist/share`, `POST /pick-requests`, `POST /pick-requests/:id/answer` и `POST /share-links` возвращают `{ url, code }`. `url` — `https://<домен>/s/<код>`.
- Код — 10 случайных символов `[A-Za-z0-9]` (около 59 бит). Перебрать нельзя, к тому же `GET /share/:code` с лимитом.
- Ссылка на вишлист **живая**: ведёт на текущий вишлист, а не на снимок. У владельца одна такая ссылка, повторная отправка даёт её же. «Перевыпустить ссылку» (старая перестаёт работать) — позже, поле `revoked_at` уже есть.
- `GET /share/:code` отвечает по виду ссылки:
  - `{ kind: "wishlist", ownerId, wishlist }` — гостевой вид, как у `GET /users/:id/wishlist` мока, плюс адреса фото своих желаний;
  - `{ kind: "pick_request", request }`;
  - `{ kind: "pick_answer", answer, request }` — `request` только автору запроса, остальным `null`;
  - `{ kind: "plan", planId }` и `{ kind: "santa", gameId }`.
- Ссылки нет или она закрыта — `NOT_FOUND` «Ссылка больше не работает».

### 6.3 Превью

Фронт — статика и превью не соберёт. Поэтому адрес `/s/<код>` обслуживает сервер:
- отдаёт маленькую HTML-страницу с `og:title`, `og:description`, `og:image`, `og:url`, `twitter:card=summary_large_image`;
- человека сразу переводит на экран фронта (`<meta http-equiv="refresh">` и `location.replace`): `/w/?s=<код>`, `/pick/?s=<код>`, `/pick/answer/?s=<код>`, `/plans/join/?id=…`, `/santa/join/?id=…`. Боты мессенджеров JavaScript не выполняют и читают теги.

Тексты (PM поправит в DESIGN §9):
- вишлист: «Вишлист Айгерим» / «на день рождения, 14 марта · 12 желаний»;
- ссылка-фильтр: «Азамат хочет подарить тебе подарок» / условия;
- ответ: «Айгерим выбрала 5 подарков»;
- план: «Айгерим зовёт: «Пятница вечером»»;
- Санта: «Тайный Санта «Офис, Новый год»» / «бюджет 2 000 сом, обмен 27 декабря».

Правила:
- в превью не попадают сообщение владельца, заметки и своё название значимой даты;
- картинка — общая `og.png` фронта (1200×630) по абсолютному адресу. Своя мини-открытка — позже;
- все тексты из базы экранируются: имя — это ввод пользователя;
- ссылки нет или закрыта — страница с общими тегами и текстом «Ссылка больше не работает».

**Адрес.** Снаружи ссылка — `https://<домен>/s/<код>`. Если фронт на Cloudflare Pages, путь `/s/*` направляется на сервер функцией Cloudflare: Pages Function или Worker-маршрут, выбрать в задаче по документации. Пока домена нет — `https://<адрес API>/s/<код>`.

### 6.4 Старые длинные ссылки

Не ломаем:
- Фронт декодирует `?d=`, как сейчас, экраны работают и в `remote`.
- Вишлист из старой ссылки — снимок. `POST /external-wishlists` только разбирает его и отвечает, в базу не пишет.
- Брони по снимку хранятся под `owner_ref = "ext:<id снимка>"`. Их видят другие гости той же ссылки, владелец — нет (как в демо).
- Если в старой ссылке `userId` настоящего пользователя сервера — бронь только с доступом (друг), иначе `FORBIDDEN`. Подделанная ссылка не должна трогать настоящий вишлист.
- Старая ссылка-фильтр: свайпы с неизвестным серверу `requestId` принимаются, ответ — длинной ссылкой, как сейчас.

## 7. Боты и демо-режим

- **Демо остаётся** на `https://seitek2002.github.io/swipeit/` в режиме `local`: боты, демо-панель, перемотка, «Смотреть как». Сборка без `NEXT_PUBLIC_API_URL` ничего не меняет.
- **Демо и продукт — разные сборки и разные адреса.** Демо (`local`) — github.io и, если так решат по T26, второй адрес на Cloudflare. Продукт (`remote`) — свой домен (§14.10).
- **`lan`** не развиваем, но не ломаем: им удобно проверять без интернета.
- **Ботов на сервере нет:**
  - в продукте друзья — живые люди, поддельные друзья с поддельными вишлистами путают;
  - движок ботов читает базу целиком (`api.db.read()`), под PostgreSQL его пришлось бы переписать;
  - показ одному человеку остаётся в демо.
- **Часы настоящие**, перемотки нет. Для обратных отсчётов клиент сверяет время по `now` из `/v1/health`, как в LAN, но без смещения.
- Тесты дедлайнов и жеребьёвки по дате — с подставными часами, а не перемоткой.

## 8. Каталог

- Пока источник — `catalog/` (Товаровед). При деплое в образ сервера кладутся `catalog/*.json` того же коммита, что и фронт.
- Сервер читает их при старте тем же `catalog-parse`: битые записи пропускает и пишет в лог. Держит в памяти — 120 подарков и 50 занятий занимают сотни КБ.
- Фото каталога отдаёт фронт статикой, как сейчас. Сервер отвечает теми же путями `/catalog/...`, клиент добавляет `basePath`.
- Обновление каталога = коммит в `catalog/` → CI выкладывает сначала фронт, потом сервер. Так фото новых товаров уже лежат, когда сервер начнёт их выдавать.
- `GET /v1/health` отдаёт `catalogVersion` (хэш `products.json`), чтобы видеть рассинхрон.
- Товар убрали из каталога, а он в чьём-то вишлисте или в колоде плана. Сервер не падает: колода его пропускает (как мок), в вишлисте — «Товара больше нет» (текст — PM).
- Партнёрские фиды — позже: таблица `products` в базе, импорт по расписанию, `offers.checkedAt` для свежести цен. Тип `Product` при этом не меняется.

## 9. Фронтенд

### 9.1 Режим `remote`

- `ApiMode = "local" | "lan" | "remote"`.
- Сборка с `NEXT_PUBLIC_API_URL` (например `https://api.<домен>/v1`) → режим `remote`, без проверки `/api/health` на своём адресе. Без переменной — как сейчас: `lan` или `local`.
- Сервер не ответил при запуске → остаёмся в `remote` и показываем «Нет связи». В `local` не уходим: иначе человек создал бы профиль в браузере и потом потерял его.

### 9.2 Что меняется в `shared/api`

- **`remote-transport.ts`** — как `httpTransport`, но:
  - адрес из `NEXT_PUBLIC_API_URL`;
  - `Authorization: Bearer` вместо `x-user-id`, плюс `x-client-build`;
  - тайм-аут 15 секунд, один повтор GET при обрыве;
  - новые коды `UNAUTHORIZED`, `RATE_LIMITED`, `INTERNAL`.
- **`mode.ts`** — третий режим.
- **`<domain>/requests.ts`** почти не меняются:
  - `url` в ответах ссылок бывает абсолютным — использовать как есть;
  - новые запросы: `loginTelegram`, `logout`, `deleteMe`, `getShare(code)`, `createShareLink`.

### 9.3 Остальное

- **Сессия:** токен в localStorage, `activeUserId` — из `/me`. На `401` — экран «Сессия закончилась» (§3.2).
- **`app/environment.ts`, ветка `remote`:** транспорт, WebSocket с `hello { token }`, часы по `/health`, фото через сервер (`setRemoteImageStore`), адрес ссылок — от сервера.
- **Не запускаются:** боты, планировщик `/plans/expire` и `/santa/tick` (`providers.tsx`), демо-панель, «Смотреть как», `/presence`, плашка сети, плашка «Это демо» на обучающей карточке.
- **Профиль:** «Войти через Telegram», «Выйти», «Удалить профиль» вместо демо-кнопок.
- **Экраны по ссылке** понимают `?s=<код>` (через `GET /share/:code`) и, как раньше, `?d=`.
- **Друзья** без демо-друзей — пустое состояние (текст — PM).
- **Тексты офлайна** — без «ноутбука».
- **Cloudflare Pages:** файл `_headers` с CSP (`connect-src` — адрес API и `wss://` API, `img-src` — свой адрес и API для фото). Без `Cross-Origin-Opener-Policy: same-origin`.

### 9.4 Перенос данных из демо

По умолчанию **не переносим** (§14.6). Почему:
- в демо-базе — боты, «Смотреть как» и чужие профили на одном устройстве;
- данные пришли бы от клиента, им нельзя верить как есть;
- id демо-профилей не совпадают с серверными; брони, планы и игры связаны с ботами.

Демо и продукт живут на разных адресах. localStorage продукта начинается с чистого листа сам, удалять ничего не нужно. Перенести хотя бы вишлист можно только через адрес — это задача B22, если владелец решит.

## 10. Безопасность и личные данные

- **Проверка входа.** Каждое тело, query и параметр — через zod (`parseInput`), как в моке. Лимит JSON — 100 КБ, фото — 2 МБ (клиент и так сжимает до 720px). Длины строк — из схем: имя 40, заметка 140, сообщение 200.
- **Права** — в каждом обработчике, по §4.4. Чужой id в пути доступа не даёт.
- **Лимиты запросов** (`@fastify/rate-limit`, в памяти процесса). Это стартовые значения, правим по логам:
  - всего — 300 в минуту с IP;
  - `POST /users` — 20 в час с IP (защита от «фермы» профилей);
  - `POST /auth/telegram` — 20 в час с IP;
  - `GET /share/:code` и `/s/:code` — 60 в минуту с IP;
  - брони — 30 в минуту на человека;
  - фото — 30 в час на человека, всего не больше 200.

  Если сервер стоит за Cloudflare или другим прокси, IP берётся из доверенного заголовка (`trustProxy`). Иначе лимит ляжет на сам прокси.
- **CORS** (`@fastify/cors`): только адреса фронта продукта и staging, точным списком из `CORS_ORIGINS`. Cookie нет, `credentials` не нужен.
- **Заголовки** (`@fastify/helmet`) на API. HTML коротких ссылок — без внешних скриптов.
- **Фото.** Тип — по первым байтам (`sniffImage` из LAN). Потом `sharp`: до 720px по большей стороне, кодирование заново — это убирает EXIF с геометкой. Ключ — `nanoid(21)`. Хранение — на диске сервера (том Docker), в бэкапе. Интерфейс хранилища такой, чтобы позже перейти на S3-совместимое (например, Cloudflare R2).
- **Секреты:** `DATABASE_URL`, `TELEGRAM_CLIENT_ID`, `TELEGRAM_CLIENT_SECRET`, `SENTRY_DSN`, ключи бэкапа. Они живут только в переменных окружения сервера и в секретах GitHub. В репозитории — `.env.example` без значений. Перед push — проверка `git ls-files` на похожее на ключи (как в TECH_SPEC §13). Токены, заголовок `Authorization` и тела запросов в логи не пишутся.
- **Бэкапы.**
  - Раз в сутки — `pg_dump` (сжатый и зашифрованный) и папка фото → объектное хранилище **другого** провайдера.
  - Храним 14 ежедневных и 8 еженедельных копий.
  - Раз в месяц — проверочное восстановление на staging. Первое — в задаче B18.
  - В худшем случае теряем сутки. Точнее (восстановление на момент времени) — с управляемой базой или позже.
- **Доступ к базе** — только по SSH-туннелю, порт Postgres наружу закрыт. Админки нет.

### 10.1 Личные данные — вопрос владельцу (§14.4)

## 12. Качество

- **Чистые функции** — Vitest в `packages/core`. Тесты переезжают вместе с кодом.
- **Обработчики сервера** — интеграционные тесты через HTTP (`app.inject` в Fastify) с настоящим Postgres. У каждого маршрута проверяются успех, права (чужой → 403 или 404) и ошибки входа.
- **Контрактные тесты.** Один набор сценариев на тонком клиенте `call(user, method, path, body)` запускается дважды: на моке в памяти и на сервере. Сценарии — главные пути из тестов мока:
  - порог 5 желаний, лента и вкус, «Вернуть»;
  - брони и «Мне это подарили»;
  - «Выбери подарок сам»;
  - план от лобби до «Решено»;
  - Санта от создания до «Купил»;
  - даты и напоминание.

  То, что по замыслу различается (права, приватность, друзья), — отдельные тесты только сервера.
- **Приватность** — §4.6, обязательно.
- **WebSocket** — два-три клиента: события доходят до своих и не доходят до чужих.
- **Гонки:**
  - 20 одновременных броней одного подарка — ровно одна успешна;
  - 15 участников свайпают один план одновременно — ровно одно `plan:match` на каждое совпадение;
  - два одновременных «Провести жеребьёвку» — одна жеребьёвка.
- **Нагрузка** в демо-масштабе (`autocannon` или k6) против staging:
  - 200 открытых WebSocket;
  - 50 запросов в секунду «лента + свайп + вишлист» в течение 5 минут;
  - план «Прямо сейчас» на 15 человек.

  Цель: p95 ответа меньше 300 мс на сервере, 0 ошибок, память не растёт.
- **Логи:** pino, JSON в stdout, у Docker — ротация. В каждой строке — `requestId`, маршрут, статус, время, `userId`. Без токенов, имён, текстов сообщений и тел ответов. Храним 14 дней.
- **Мониторинг:**
  - Sentry для ошибок сервера. Для фронта — позже, по решению: он добавляет JS и бьёт по Lighthouse;
  - внешний пинг `/v1/health` раз в минуту, письмо при падении.
- **`npm run check`** в корне проверяет фронт, core и сервер. Задача сдана, когда `check` и `build` зелёные.

### B01 — Каркас сервера и рабочее пространство

**Цель:** пустой сервер запускается, отвечает на `/v1/health` и проверяется в CI. Демо не меняется.

**Сделать:**
1. Рабочее пространство npm в корне: `package.json` с `workspaces: ["packages/*", "frontend", "backend"]`, один `package-lock.json`. Поправить пути в `frontend/package.json` (husky `prepare`, `catalog:sync`) и в `deploy.yml` (`npm ci` в корне, кеш по корневому lockfile). Фронт собирается, как раньше.
2. `backend/`: TypeScript strict с `noUncheckedIndexedAccess`, Node 24, Fastify 5.
   - `src/config.ts` — переменные окружения через zod. Неверные — сервер не стартует и пишет, что не так.
   - `GET /v1/health` → `{ app: "swipeit", mode: "remote", apiVersion: 1, now }`.

## 14. Решения владельца

**Решено владельцем 27.11.2026:**
- **вход** — Telegram, другие способы позже, по ситуации;
- **хостинг** — серверы компании владельца, разворачивает их администратор (B18);
- **уведомления** — Telegram-бот, тот же, что для входа: в B19 сразу просим `telegram:bot_access`;
- **друзья** — автоматически, как в §4.3.

Открыто:

### 14.1 Способ входа

| Вариант | Цена | Минусы |
|---|---|---|
| Telegram (OpenID Connect) | бесплатно | нужен Telegram; вход в отдельном окне; адреса сайта регистрируются в BotFather |
| SMS по телефону | платно за каждое SMS (цену в КР не проверял) | провайдер, защита от перебора и спама; телефон — более чувствительные данные |
| Google | бесплатно | нужен проект в Google Cloud; у части людей нет или не помнят аккаунт |
| Почта (ссылка или код) | у почтовых сервисов есть бесплатный уровень | письма попадают в спам; почтой, по допущению, пользуются реже мессенджеров |

**Рекомендация:** анонимный профиль и Telegram в первой версии. Google — вторым, если на показах будут люди без Telegram. На будущее: когда дойдём до приложения для iPhone, правила App Store могут потребовать вход через Apple наравне с другими — проверить к тому этапу.

### 14.2 Хостинг и бюджет

Варианты и цены — §11.2.

**Рекомендация:** VPS + Docker Compose. Бюджет — до $20 в месяц: сервер, бэкапы и домен в пересчёте на месяц.

Ещё нужно решить, у кого будет SSH-доступ и кто получает письма о падении: владелец, Исполнитель или оба.

### 14.3 Домен

Нужен для HTTPS API, коротких ссылок, входа через Telegram и адреса продукта.

**Рекомендация:** один короткий домен, DNS в Cloudflare.

### 14.4 Где хранить данные

| Вариант | Плюсы | Минусы |

**Рекомендация:** до публичного запуска спросить юриста:

## 15. Расхождения кода и TECH_SPEC

Найдены при подготовке этого документа. Сервер опирается на код.

1. **Маршруты, которых нет в таблице TECH_SPEC §6:** `/swipes/restart`, `/wishlist/items/:id/undelete`, `/pick-requests/:id/picks`, `/plans/expire`, `/plans/:id/join`, `/plans/:id/swipes/undo`, `/plans/:id/rule`, `/plans/:id/activities`, `/santa/tick`, `GET /activities`, `GET /demo/users`. Только в LAN — `GET /uploads/:key`.
2. **Поля моделей, которых нет в TECH_SPEC §5:**
   - `PlanSession.customActivityIds`;
   - `SantaGame.invitedIds` и `drawnAt`;
   - `ProductSwipe.variantChoice`;
   - `PickRequest.from.gender`, `PickAnswer.by.gender` и `by.userId`;
   - `Activity.imageKey`;
   - `occasion.preset` в `WishlistMeta`.
3. **Ключ брони своего желания:** в коде `custom:<id желания>`, а в TECH_SPEC — `custom:<title>`. Старое правило осталось только для старых ссылок (`sharedItemKey`).
4. **События:** в коде есть типы `trigger` и `bot:action`, у области `settings` есть тип в `RealtimeScope`. В TECH_SPEC §7 их нет.
5. **Часовой пояс:** TECH_SPEC — «по календарю Бишкека», код — местное время процесса (§2.5).
6. **Ошибки:** LAN-сервер отвечает кодом `INTERNAL` на 500, а в типе `ApiErrorCode` его нет. 413 приходит как `VALIDATION`.
7. **`/api/health` на Pages:** TECH_SPEC — 404, а в коде есть статический `public/api/health` с `mode: "static"` (чтобы не было 404 в консоли).
8. **Права в моке и LAN** — допустимо для демо, но не для сервера:
   - `GET /plans/:id` отдаёт свайпы и голоса всем, кто знает id;
   - `GET /users/:id` и `GET /users/:id/wishlist` — без проверки дружбы;
   - `undelete` принимает желание целиком от клиента;
   - `importPickAnswer` хранит ответы без автора запроса;
   - в LAN события с `by` и тосты с `forUserId` уходят всем.
9. **Документы:** `backend/` описан в CLAUDE.md как пустая папка, но в репозитории его нет вовсе. Порядок задач в EXECUTOR.md заканчивается на T25, в TASKS.md есть T26.
